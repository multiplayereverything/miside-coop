# Code audit, 2026-11-10

What the mod is missing and what should have been built differently. Written from reading the code (three review passes: network, players/world, tests) plus the saved lab and session logs.

**Status of every finding below:** read in the code, **not reproduced in the lab** unless it says so. By the project's own rule each one needs a failing `MT-CHECK` before a fix. Items marked *spot-checked* were re-read line by line after the review pass reported them; the rest are a reviewer's reading and may be wrong.

## Status, 2026-11-10 (later)

Fixed, each from a tour that failed first: 2.7 saves guard (`savesguard`), 1.1 Main Character (`pressrace`), 2.1 reconnect before migrating (`blip`), 2.9 minigame owner leaves (`ownerleaves`). Explained: both "own event threw" cases are the game's own. Added: lagged and three-player Scene 2 runs. Not reproduced: 2.10 held items. Everything else below is still open.

## 1. Design choices to change

| # | What was done | Why it hurts | What to do instead |
| --- | --- | --- | --- |
| 1 | **Each PC decides for itself who the Main Character is** (`ownRequests`, `momentMine` in `StoryLog.cs`). The host's log entry says only "this was a request", not who asked. | A press that is refused, or that loses a race, leaves its key in `ownRequests`. The next log entry for that object is then treated as this PC's own, so two PCs play the Main Character at once. *Spot-checked* (`StoryLog.cs:157`, `:424`, `:527`). | The host writes the asker's id in every log entry; a PC is the Main Character only when that id is its own. Delete `ownRequests`. Protocol change: bump `Wire.Version`. |
| 2 | **Two story sync systems**: the story log (Scenes 1–17) and the older relay (Scenes 18–21). | Every hook has two behaviours, and every fix has to be made and tested twice. Scenes 6, 8, 9, 11, 12, 14, 16, 17 were moved to the log in one commit with little testing. | Finish the move, then delete the relay path. One system. |
| 3 | **"The host settles it" is written in the docs but not in the code** for minigames, the visual novel and deaths. | Minigames: last claim wins per PC, so two simultaneous starts can leave both players watching or both playing (`Minigames.cs:176-201`, *spot-checked*). Novella: a click carries no position, so two clicks on one line skip a line for everyone (`Novella.cs:30-36`). Deaths: one global 6 s quiet window swallows a second real death and is armed even when the object isn't found (`Deaths.cs:15-33`, *spot-checked*). | Put these on the story log too: a request, the host decides, one ordered answer. |
| 4 | **Objects are named by long path strings with sibling numbers**, and several places compute the key at call time (`Seeds.cs`, `Props.cs`, minigame end) instead of using the key recorded at chapter start. | Sibling numbers change as the story spawns and destroys objects, so a late key can name a different object or nothing. Strings of 80+ characters go in every packet. | A table built once at chapter load (key → small number), the same on every PC; numbers on the wire; a hash of the table compared at the start barrier so a mismatch is caught in the first second. |
| 5 | **Nothing cleans up after a player who leaves.** Peer removal destroys the body and nothing else (`Net.cs:60`, `:216`, *spot-checked*). | A leaving minigame owner blocks that minigame until the chapter changes; their held item stays hidden in the world; the Scene 3 hand chain freezes if they led it. | One `PeerLeft(id)` that every feature registers with. |
| 6 | **Periodic scene-wide searches** (`FindObjectsOfType` every 2–3 s for cutscenes, props, the console screen). The cutscene one runs even in single-player with the mod installed (`Cutscenes.cs:22-32`). | Frame hitches in big chapters. | Register once per chapter, like `SceneKeys.RegisterItems` already does. |
| 7 | **No fast tests.** The only test is a real game tour (1–10 minutes each, one at a time). | Ordering, races, lag and reconnects can't be tried cheaply, so they mostly weren't. This is the main reason for the gaps in section 3. | Move the pure logic (story log, gates, who-wins rules) behind an interface with no Unity types and test it in a normal test project with simulated peers, delay, loss and reordering. Thousands of cases per second. Keep the tours for what only the game can show. |
| 8 | **Lab commands work in the released mod.** `lab-…` notices are handled with no `LabMode` check (`Net.cs:162`, `:290-296`, *spot-checked*). | Any player can send them to the others. | Gate on `LabMode`. |
| 9 | **One very large partial class with static state**, 136 `catch` blocks, 19 of them empty. | Hidden failures, and state that survives a session when it shouldn't (`saveHashes`, `handLeader`, `mobileHolder`, `consoleReplies`). | Per-chapter and per-session state in two objects that are replaced, not reset field by field. |

## 2. Bugs found by reading

### Network (all *spot-checked* unless noted)
1. **A single client's connection blip splits the session.** Any client link loss calls `TryMigrate()` (`Net.cs:56`), and the lowest-id client starts hosting at once. It should first try to reconnect to the host it had.
2. **The rejoin after migration is one attempt**, 4 s later, Steam first with no fallback (`Migration.cs:44-64`).
3. **Hello is fully parsed before the version check** (`Net.cs:86-93`), so a different version can fail with a parse error instead of the "versions differ" message.
4. **The mid-chapter gate ignores `rejoining`** (`Net.cs:92`, `:111`): the flag is read and never used; the gate is "host is mid-chapter and the scenes differ".
5. **Save text limits disagree**: saves up to 16384 bytes are sent, the text writer throws above 4096, and an exception there drops the peer. The user's saves are 2–31 bytes, so this needs an unusual file.
6. Not individually checked: last packets lost on close and clients have no leave case; the accept loop dies on any exception; unaccepted connections hold slots with no deadline; every Steam packet is sent reliable.

### Saves
7. **A client's own saves can be overwritten with no backup** (`Saves.cs:97-100`, *spot-checked*). `BackupSaves` swallows its failure, and the write happens anyway. One-line guard: refuse to write when the backup marker isn't there. **Fix this first; it is the only finding that can lose a player's progress.**
8. The host never mirrors a deleted save, and `saveHashes` isn't cleared between sessions (`Saves.cs:51-68`).

### Players, world, story
9. Minigame owner disconnects → minigame owned forever (`Minigames.cs:199-205`).
10. Hand items stuck hidden or visible when the holder leaves or their body is rebuilt (`Items.cs:109-157`).
11. A body that was hidden (cutscene) slides from its old spot through walls when shown again; only jumps over 10 m snap (`Avatars.cs:280-291`).
12. `MinigameEnding` can stay set if the game's end method throws, which silently drops that PC's later story relays (`Minigames.cs:143-162`).
13. Animator catch-up assumes a 2 s clip and clamps loops to their last frame (`WorldState.cs:157-159`).
14. Seeded random rolls drift for the rest of a chapter after one unequal call, and are seeded even in single-player (`Seeds.cs:16-27`).
15. Dialogue: the host list is cut at 16 lines before sorting; a client skips any line not in it (`Dialogue.cs:75`).
16. Cutscene time has no latency compensation; above about 250 ms of ping plus jitter the client's timeline is pulled back five times a second (`Cutscenes.cs:106-112`).
17. In a log chapter `ApplyStory` sets `interactive.active = true` before clicking (`WorldSync.cs:195-230`), so a second request for an object that was already pressed may run it twice instead of being refused.
18. Performance: the Scene 3 hand chain enumerates every skeleton about 24 times a frame with 4 players (`HandHold.cs`); a visibility string is built 15 times a second (`Bones.cs:157-165`); the prop stream always sends the same first 20 props (`Props.cs`).

## 3. What the tests don't cover

- **Checks that can't fail.** Several checks assert the mod's own counters, or are logged as passed unconditionally (`story.sent`, `death.sent`, `minigame.*`, dialogue and trigger counters). Some pass with zero samples (`cards.oneplays`, `tv.oneplays`, `interactions.pressed`).
- **The verifier is blind to "the game's own event threw".** It fails only on `MT-MODERROR` (`tests/verify-lab.py:255`, *spot-checked*). Such lines exist in passing runs: `TimeInToilet#10` in scene2 and `AnimationPlayer TakeMobile#2` in scene14, on host and client alike. Cause unknown.
- **22 `.Click()` calls remain in 11 tour files** (*spot-checked*), a path real play never takes.
- **39 tours are outside the suite**, including every regression tour written on 2026-11-07/09 and every chapter tour after Scene 3. Scenes 8, 9, 10, 12 and 16 have no tour at all.
- **Nothing runs with latency.** The suite sets no `-Lag`. Every race above needs lag to show.
- **3–4 players only ever load a scene.** No story is played with more than two.
- **The client is never the Main Character through a chapter.** `-mt-pilotboth` silently falls back to the host pressing.
- **Never played:** a chapter-to-chapter transition, migration mid-chapter, a death with a client victim asserted on game state.
- `pilot.acted` needs 3 actions and fails in Scenes 11, 14 and 17 (6, 2 and 9 actions: the pilot runs out of things it knows how to do).
- `docs/SYNC.md`'s "proved by tour" column is wrong in several rows; `docs/HANDOFF.md` is stale about the suite; `AGENTS.md` says the start barrier times out at 25 s, the code holds 45 s.

## 4. Unexplained, seen in logs

- **Scene 17:** the client has one more light than the host for about 25 s ("PointLight Realtimedark444", enabled only on the client). **Scene 20:** the client has "Light0422", the host has none. Both from the `chapters` run of 2026-11-09. `MT-LIGHTS` logs names, not paths, so the objects aren't pinned down yet.
- **Scene 20's arena lights change every couple of seconds**, and the lighting check can't judge them: 81% of samples differ in the saved `scene20` run (2026-11-09). The client shows a state several seconds after the host showed it, so the cycle may be out of step between PCs. Not verified either way; `scene20` is not in the suite.
- **67 "MT-LOG refused" lines in real sessions.** A refused press is what arms finding 1.1, so this is likely not rare in real play.

## 5. Order of work

1. Saves guard (2.7): small, and the only data-loss risk.
2. Asker id in the log entry (1.1), with a two-player race tour under lag as its failing test.
3. `PeerLeft` cleanup (1.5) with the minigame and held-item cases as tests.
4. Reconnect before migrating (2.1, 2.2).
5. Make the verifier fail on "own event threw", then explain the two that exist.
6. Add lag and a 3-player story run to the suite; put the regression tours in it.
7. Minigames, novella and deaths onto the log (1.3), then retire the relay (1.2).
8. The offline test project (1.7). It costs the most and pays back on every later change.

## 6. Done well

Packet framing and text bounds; the host's op whitelist and overwriting the sender id on relays; `Step(...)` isolation with per-step timing; the save backup marker and restore after a crash; one explicit per-chapter reset list; room-state tracking spread over frames; the story log's ordering itself.
